# Backend and database audit — October 16, 2026

Status: **not ready for production release**. The work below repairs verified defects and adds an executable database deployment path. It does not establish that hosted data is authentic, every feature is complete, or web/mobile have full parity.

Scope: static review of application routes/services/models, relational metadata/migration checks, actual isolated PostgreSQL 17 and MongoDB 8.0 integration tests, and focused API regressions. Authentication, payments, upload security, AI routes, moderation and privacy endpoints were assigned to the security/root workstream; frontend/mobile and their coverage inventory were assigned separately. Existing working-tree edits were preserved. No hosted database was accessed or mutated.

## Feature coverage and remaining release blockers

| Feature group | Evidence / remaining work |
| --- | --- |
| Scheduling | Active-slot uniqueness and positive duration are database-enforced and tested. Follow-up security work serializes availability writes by locking the counsellor parent row, rejects overlap/past times, protects booked/history slots, normalizes UTC, and tests concurrent creates on PostgreSQL. Free cancellation locks appointment/slot, rejects started/completed appointments and releases the slot; joins require a confirmed matching appointment and reject expired/deleted sessions. Real Daily/provider acceptance and reschedule workflow remain unverified/incomplete. |
| Financial data | Follow-up security work verifies provider identities/amount/currency and expanded charge refund/dispute state before booking redemption. Paid cancellation and wallet top-ups fail with 503 until verified refund/ledger handling exists. Refund/payout accounting and ongoing provider reconciliation remain unimplemented. Existing dummy payments and seeded wallet balances must be identified in a backed-up production copy; this audit did not delete or certify them. |
| Chatbot/history | Mongo conversation data and PostgreSQL message counters have separate commits; a crash can disagree. History reads load the whole conversation document, which grows toward MongoDB document limits. backend/app/services/chatbot/chatbot_service.py:179; :188. Streaming persistence/context recovery and multi-process delivery require acceptance/load tests. |
| Clinical content and assessments | Content is database-backed, but several async endpoints call synchronous Mongo operations directly. Disorder ID allocation reads the latest document and is not atomic; bulk import reads the whole file, uses a different ID format and can exceed RAM. backend/app/routes/assessments/assessments.py:26; backend/app/services/admin/content_management.py:47; backend/app/utils/unique_id_generation.py:72. Scoring currently trusts submitted option scores; clinical instrument validation/versioning/licensing is not established. |
| Account lifecycle/privacy | Unsafe patient/counsellor self-delete and administrative privacy endpoints now return 503 without mutation. Cross-database erasure, provider cleanup, retention and auditable recovery jobs remain unimplemented; a clear unavailable state is not erasure support. backend/app/services/normal_user/user_management_service.py:109; backend/app/services/counsellor/counsellor_management_service.py:99. |
| Community | Feeds/groups require authenticated normal users; responses omit account identifiers for all authors, including anonymous posts; payloads/IDs/actions are validated and storage failures return 503. Security regressions cover access/anonymity/errors. Private membership policies, full moderation lifecycle and one-reaction-per-user storage remain unimplemented; counters can be incremented repeatedly. |
| Exercises/therapy plans | The catalog is real database content. Assignment/completion APIs, clinician authoring, therapy plans and versioned clinical approval are not established by creating collections. Related UI cannot be certified as fully operational. |
| Tracking | CRUD and atomic writes tested. Medication taken state is a boolean, not a dated dose/adherence ledger. Goal streak is a completion transition count, not a proven longitudinal daily streak. Wearable ingestion/provider consent and integration do not exist in the reviewed routes; null telemetry is expected until a real source is configured. |
| Notifications/direct messages | SQL models and access-pattern indexes exist. Push delivery, receipt tracking, worker retries, WebSocket scaling, retention and high-volume pagination need acceptance/load tests. |
| Dashboard/admin analytics | Personal dashboards use actual queries. Other analytics definitions and older unbounded lists need validation against real fixtures and production query plans. Existing production records may contain synthetic data from older code. |
| Production operations | Encrypted backups/restores, retention, least-privilege roles, monitoring, error tracking, provider configurations, load testing and actual staged data migration remain external gates. No claim of security/compliance certification is made. |

## Validation

Command run from backend:

~~~powershell
$env:SARVUDAY_RUN_DATABASE_TESTS = '1'
.\venv\Scripts\python.exe -m pytest tests/test_database_tracking.py -q
~~~

Initial result: 20 database/tracking tests passed using reserved loopback-only disposable PostgreSQL 17 and MongoDB 8.0 containers. Final follow-up result: **74 backend tests passed (21 database/tracking and 53 security tests)** with the same isolated databases; run python -m pytest tests -q with SARVUDAY_RUN_DATABASE_TESTS=1 for the complete suite.

Coverage includes ORM registration, offline SQL compilation, fresh live migration and clean Alembic drift, legacy list preservation, phone-only identities, concurrent active-booking constraints and cancellation history, invalid slot duration, asyncpg prescription create/list and ownership, both role dashboard queries, strict Mongo input validation, zero automatic seed data, idempotent provisioning, real empty catalog/goals/telemetry, concurrent medication/goal updates, cross-user mutation rejection, input scale/bounds, actual correlation, and awaited contact persistence/503 errors.

The suite does not validate hosted data, live Firebase credentials, Stripe settlement, Daily calls, device hardware/120 Hz performance, full page interactions, or production-scale memory/query performance. Existing Pydantic v2 deprecation warnings remain; migration to ConfigDict/current serializers is needed before adopting Pydantic v3.

MongoDB schema version is now 2, admitting the truthful manual crisis classification; reapply provisioning before deployment. See docs/audits/security.md for final security findings and the distinction between unimplemented features and externally unverified behavior. Follow backend/DATABASE.md for deployment, existing-schema adoption, connection budgets and reproducible tests. Technical implementation was checked against [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html), [SQLAlchemy pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html) and [MongoDB validators](https://www.mongodb.com/docs/manual/core/schema-validation/).
